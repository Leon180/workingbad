# Grill: Slice C Graph UI Design

- **Date**: 2026-06-09
- **Phase**: 1, Slice C (位於 Slice B Web UI merge 之後、v0.1.0 tag 之前)
- **Status**: Locked — 進入實作（小 PR 切片，從 layout package 開始）
- **Trigger**: 使用者明確要求「右邊是 goal、中間散布節點 + 線連回去，像 git 但更美觀」
- **Workflow**: 多 agent grill — search-specialist 業界 prior art + architect 架構可行性 + ui-ux-designer 工作流與美學

## 1. 問題定義

Slice B 表格版上線後，使用者反饋 UI「不太行」。要求從表格切換到節點 + 邊的圖形視覺：

- 5 種節點型別（goal / activity / research / decision / discuss）
- 5 種邊關係（part_of / relates_to / derived_from / blocks / iteration_of）
- bitemporal time-travel 已 ready (PR #9)
- 規模 50–5000 entries
- ROADMAP Slice B 原寫「零 graph」，使用者 override

## 3. 鎖定的最終設計

### 3.1 技術棧

- **0 JavaScript framework**（守住 ROADMAP「單一 Go binary」）
- 純 **html/template** 產 SVG
- Layout 在 Go 端跑（Sugiyama hierarchical 簡化版自寫 ~300 行；後續可考慮 `gonum.org/v1/gonum/graph`）
- **htmx** 終於派上用場：click node → `hx-get` 換 detail panel；filter 變更 → 換整張 SVG
- pan/zoom 用 ~30 行 vanilla JS（不算 framework）

### 3.2 Layout

- **Sink-anchored DAG**：goal 在右側錨定（rank 0），`part_of` 反向（被 part-of 的指向 goal）
- 同 rank 內 **barycenter ordering** 降低 edge crossing
- `iteration_of` 走 **獨立時間軸 lane**，跟主 DAG 分通道（避免 cycle 把 hierarchical 算法搞醜）
- 多 goal：右側垂直分 swimlane，每個 goal 一條

### 3.3 節點視覺

| 型別 | 形狀 | 顏色 | 預設顯示 |
|---|---|---|---|
| goal | 圓角矩形（最大）| 藍 | title + status badge |
| activity | 小圓點 | 灰 | title 截 30 字 |
| decision | 鑽石 | 橙 | title |
| research | 圓 | 綠 | title |
| discuss | 六邊形 | 紫 | title |

**Goal status 用邊框樣式**（避免再吃顏色預算）：
- open = 虛線邊框
- in_progress = 實線 + 輕微 glow
- done = 填色變淡
- archived = 半透明

**Hit area ≥ 44px**（避免「點不到」沮喪）。

### 3.4 邊視覺

| 關係 | 樣式 | 顏色 | 預設顯示 |
|---|---|---|---|
| part_of | 實線最粗，無箭頭 | 中性深色 | ✅ 主骨幹 |
| derived_from | 實線 + 箭頭，較細 | 中性 | toggle |
| relates_to | 虛線（dash），無箭頭 | 淺中性 | toggle |
| **blocks** | 虛線 + 箭頭 + **X 符號中點** | **紅** | ✅ 永遠顯示（最高優先警示） |
| iteration_of | 點線（dot） | 中性 | toggle（時間軸獨立通道） |

**Colour-blind 對策**：blocks 不只靠紅色（加 X 符號）；其餘關係靠樣式區分。

### 3.5 互動

優先順序（從高頻到低頻）：

1. **click node** → htmx swap detail panel（每次必用）
2. **hover** → tooltip 顯示 body preview（低成本高頻）
3. **pan / zoom** → ~30 行 vanilla JS（v0.1.0 必做）
4. **search highlight** → 輸入關鍵字非匹配淡出（每週 1-5 次）
5. **keyboard nav**（tab / j-k / enter）→ Phase 2
6. **drag to reposition** → **永遠不做**（auto-layout 夠用）

### 3.6 Time-travel

- 頂部 toolbar 放 **slider**（不放動畫，純 snapshot 切換 — 拖完才重 layout）
- URL `?at=<RFC3339>` 同 Slice B 表格版（兩個 view 共用 query param，URL 直接複用）
- supersede chain **不放主 DAG**；click 節點後 detail panel 顯示版本歷史
- 主 DAG 永遠只顯示「當前 valid 版本」

### 3.7 跟 Slice B 表格版的關係

- **並存**：表格 = grep-able audit；graph = 探索與 retrospective
- **預設 `/` 仍是表格**，graph 在 `/graph`
- goal detail 頁加 tab「list / graph」二選一
- URL `?at=` 兩 view 一致

## 4. 必須先解的 3 個技術風險（agent 紅旗）

| 風險 | 來源 | 緩解 |
|---|---|---|
| **`iteration_of` 是 cyclic，hierarchical layout 會醜** | architect H1 | 分獨立時間軸 lane，不混進 `part_of` 主幹 |
| **`?at=` 時 edges 的 supersede chain 跟 entry chain 不同步** | architect H3 | 先實作 `EdgesAt(asOf, filter)` repository method（Slice B 已 deferred）→ graph version 才能跑 time-travel |
| **同 goal 多 entry `part_of` 時 edge crossing 爆炸** | architect H2 | Sugiyama barycenter 救 80%；剩下需要 collapse rule（max edges per node 截斷 + click 展開） |

## 7. Design Intent

> **workingbad graph view 的核心 promise**：讓工程師在 30 秒內看清「自己今天的工作在哪個 goal 的哪個位置，有沒有東西被 block」，而不是讓工程師管理一張圖。圖是工作記憶的鏡子，不是工作本身。預設視圖永遠偏向 less-noise，細節藏在 click 之後；goal 固定在右側作為視覺錨點，所有 activity 和 decision 從左邊向它匯流，這個方向性告訴使用者「你做的每一件事都有去處」。唯一打破低調視覺的是 blocks 邊：它要夠顯眼，因為被 block 的 goal 是工程師最需要立刻知道的事。

— ui-ux-designer agent，採用為實作北極星。
